**根因还是 pass1 那个**：没认出窗口是定长的，于是按变长窗口的肌肉记忆写了个 `valid()`，

```python
if r - l + 1 > len(s1):      # 窗口超长, 把 s2[l] 吐回去
    if s2[l] in cnt:         # 这个 in 判断必须和右边的对称,
```

## 三条砍掉的路

### 1. 让 `need` 在计数归零时 `del` 掉键，用 `len(need) == 0` 判定 —— 错的

**滑动窗口的「进」和「出」必须是一对逆操作，而 `del` 是破坏性、不可逆的。**
字符移出窗口时 `need` 里已经没这个键，`if s2[l] in need` 恒 False，需求恢复不回来。

反例 `s1="abc" s2="abxc"`：窗口滑到 `"bxc"` 时 `need` 已空 -> 假阳性 True（正确答案 False）。
随机对拍 20000 组错 925 组。

注意这和 `win` 里残留 `{'a': 0}` 的区别 —— 差别不在「删不删」，在**删掉的东西是不是可恢复的**：
`win` 编码「窗口里有几个」，缺席 == 0 是忠实表示，`+= 1` 能复活；
`need` 编码「s1 需要什么」这个**恒定事实**，删了配上 `in` 守卫就再也还不回来。

一条更一般的原则：**别用容器的 size / 键的存在性表达状态，状态就显式存一个 int。**
上面那个错法本质是在用 size 隐式编码状态量，逼着自己为了把 size 压到 0 去破坏数据本身。

### 2. 增量维护一个标量 `missing`，把 O(26n) 降到 O(n) —— 对但是负收益

思路：每次滑动只有 2 个格子变了却扫 26 个，看起来白做功。维护 `missing = 还差几个字符`，
`push` 时「先判断 `need[c] > 0` 再 `-= 1`」，`pop` 时「先 `+= 1` 再判断 `need[c] > 0`」，
判定退化成一次整数比较。（两边顺序必须相反，判的是同一件事「c 处于欠账状态」，
而这状态由计数为正的那一侧决定：进是修改前为正，出是修改后为正。）

`missing == 0` 就够，不用另外查超量：窗口长恒为 n，`sum(need.values())` 恒为 0，
`missing == 0` 意味着每个 `need[c] <= 0`，一堆非正数加起来是 0 只能全是 0。

**但在 CPython 里实测更慢**，因为 `win == need` 的 26 次比较在 C 层一个循环里跑完，
约等于一两条字节码；而维护标量的每一行都是解释器在跑。用 C 层的 26 次换解释器的 6 次，前者赢。

> 判据：在 Python 里，「把循环推给 C」常常比「降低渐进常数」更重要。
> 增量维护要到窗口状态不是 26 个小整数时才划算 —— 比较本身 O(k) 且 k 大、
> 状态是复杂对象、或换成 C++/Java 手写比较循环。

通用套路本身还是成立的：窗口里凡是要做全量扫描，先问一句「这个量能不能增量更新」。

### 3. `list(26)` + `ord(c) - 97` 代替 Counter —— 更快但不值

同一个算法，换掉手工下标映射。实测（CPython 3.12，`len(s2)=1e4`，构造成全程无命中走满整个 s2，每例 20 次）：

| n=len(s1) | Counter | list(26) | 倍数 |
|---|---|---|---|
| 2 | 19.52 ms | 1.40 ms | 13.9x |
| 10 | 12.84 ms | 1.98 ms | 6.5x |
| 26 | 10.59 ms | 1.48 ms | 7.2x |
| 100 | 10.13 ms | 1.37 ms | 7.4x |
| 1000 | 8.71 ms | 1.28 ms | 6.8x |
| 5000 | 5.19 ms | 1.14 ms | 4.5x |

三种写法横比（每用例 20 次取平均）：

| 写法 | s1=1e4/s2=1e4 | s1=2/s2=1e4 | s1=26/s2=1e4 |
|---|---|---|---|
| 闭包 push/pop + Counter（路 2） | 1.92 ms | 3.54 ms | 3.60 ms |
| 内联标量 + list(26) | 1.36 ms | 1.76 ms | 1.72 ms |
| 两数组比较（路 3） | 1.11 ms | 1.28 ms | 1.34 ms |

n 小时窗口比较次数最多，差距最大。最坏 19.5 ms 离 LeetCode 的秒级限时还远，
这点常数换可读性划算，所以默认写法认 Counter 版。

但字符集固定 26 且常数极小，实践中不必要」—— 说明你知道那条路，同时给出了不走的理由。
只会写 O(26n) 和「知道 O(n) 但选择不写」是两回事。

再往上没有了，O(n) 是下界 —— s2 总得读一遍。（想把 26 个计数压成一个整数做滚动哈希的：
计数不是集合，位运算表达不了重数，随机哈希又要处理碰撞，收益为负。）
