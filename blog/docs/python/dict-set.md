# dict / set

## 一句话

**开放寻址的哈希表**。按 key 查、插、删均摊 O(1)；key 必须可哈希；`dict` 记住插入顺序，`set` 不记。

## 底层长什么样

起点是 [structures/hash-table.md](../structures/hash-table.md) §0 里那个直觉版本：**一个大数组，每格一个小 list**。
CPython 的 `dict` 从这里出发改了四次，每一次都是在解决上一版的一个问题：

| 步 | 上一版的问题 | 改成 |
|---|---|---|
| 1 | 每个小 list 都是单独的对象，查找要多跳一次指针，还占额外内存 | **开放寻址**：去掉小 list，元素直接放进大数组；撞车了就去找别的空格 |
| 2 | 「往后一格」找空位，撞车的元素会连成一大片 | **跳着找**：按一个公式跳到离得远的格子 |
| 3 | 删除一个元素会把别人的查找路线截断 | **墓碑**：删除只做标记，不清空 |
| 4 | 开放寻址必须留很多空格才快，每个空格都占一整条记录的空间 | **拆成两张表**：空格只占 1 字节；顺带得到「按插入顺序遍历」 |

### 第 1 步：去掉小 list → 开放寻址

拉链法里每个小 list 都是一个独立的对象，散落在内存各处。查一次要先读大数组、再顺着指针跳到小 list，
每个小 list 本身也要占额外的内存。

开放寻址的想法是：**不要小 list 了，元素直接住进大数组的格子里**。撞车了怎么办？去找另一个空格子住。

```
拉链法                         开放寻址
格子 3: [3, 11]                格子 3: 3      格子 4: 11      11 发现 3 号被占，换个空格住
```

查找时也按同样的规则走：先看 3 号，不是 11；再看下一个候选格，是 11，找到了。走到空格还没找到，就说明不存在。

### 第 2 步：被占了往哪找 → 跳着找

最简单的规则是「往后一格」（`i + 1`）。问题是撞车的元素会**连成一片**：3 号被占就放 4 号，
下一个落到 3 或 4 的就放 5 号……这一片越长，落进来的元素就要走越远才找到空格，又反过来让这一片变得更长。

CPython 的规则是跳着找：

```python
perturb = hash
i = hash & mask                    # mask = 表长 - 1，hash & mask 等价于 hash % 表长
while 这一格被占且不是要找的 key:
    perturb >>= 5
    i = (5 * i + perturb + 1) & mask
```

- **`5 * i + 1`**：每次跳到离得较远的格子，不会和邻居连成一片。而且在长度是 2 的幂的表上，
  这个递推会把每一格都走到一遍，所以只要表没满，一定能找到空格。
- **`perturb`**：`hash & mask` 只用到了 hash 的最低几位，低位相同的 key 会一直撞在一起。
  `perturb` 每次右移 5 位，把 hash 的高位一点点掺进来，让它们的路线早早分开。几轮之后 `perturb` 变成 0，就只剩 `5 * i + 1`。

### 第 3 步：删除会断路 → 墓碑

开放寻址有一个拉链法没有的麻烦。假设 11 是因为 3 号被占才住进了别的格子，现在把 3 删掉、清空 3 号格。
下次查 11，从 3 号出发，一看是空格，就以为 11 不存在 —— 其实 11 就在后面。

所以删除不清空，只在那一格留一个**墓碑**，意思是「这里有过东西，查找请继续往后走；插入可以重新用这格」。
墓碑攒多了也会拖慢查找，下次扩容时一起清掉。

### 第 4 步：空格太浪费 → 拆成两张表

开放寻址有个代价：**表越满，找空格要跳的次数越多**，而且是急剧变多（粗略估计是 1/(1 − 满的比例) 次：
2/3 满大约 3 次，90% 满大约 10 次）。所以 CPython 的规矩是 `dict` 最多装到 2/3 满就扩容，
也就是说至少有 1/3 的格子永远是空的。

3.6 之前，每一格都是一整条 `(hash, key, value)` 记录，在 64 位机器上是 24 字节，空格也一样占 24 字节。
**这 1/3 的空格全是浪费。**

3.6 的改法是把一张表拆成两张：

```
indices  稀疏，长度是 2 的幂（最少 8）。每格只存一个小整数：entries 里的下标，或者「空」/「墓碑」
entries  稠密，只存真正有的记录 (hash, key, value)，新来的一律追加到末尾
```

- 跳来跳去找空格这件事只在 `indices` 里发生。它的每一格只是一个小整数，表小的时候 1 字节就够，
  空着也只浪费 1 字节，而不是 24 字节。
- `entries` 不留空格，有几条记录就占几条的地方。
- **顺带的好处**：`entries` 是按插入顺序追加的，遍历 `entries` 就是按插入顺序遍历。
  这个「`dict` 有序」最初只是省内存的副作用，后来在 3.7 被写进了语言规范。

### 走一遍：`d[3] = 'a'; d[11] = 'b'; d[6] = 'c'`

小整数的 hash 就是它自己。`indices` 长度 8，所以 `mask = 7`，起始格是 `hash & 7`：

```
d[3]  = 'a'   3 & 7 = 3   indices[3] 空 → entries 追加到 0 号，indices[3] = 0
d[11] = 'b'  11 & 7 = 3   indices[3] 被占 → 跳：perturb = 11 >> 5 = 0，i = (5*3 + 0 + 1) & 7 = 0
                          indices[0] 空 → entries 追加到 1 号，indices[0] = 1
d[6]  = 'c'   6 & 7 = 6   indices[6] 空 → entries 追加到 2 号，indices[6] = 2

indices: [ 1, -, -, 0, -, -, 2, - ]
entries: [ (3, 3, 'a'), (11, 11, 'b'), (6, 6, 'c') ]
```

查 `d[11]` 就是把这条路再走一遍：先看 `indices[3]`，指向 entries[0]，key 是 3，不是 11，继续跳；
下一格是 `indices[0]`，指向 entries[1]，key 是 11，命中，返回 `'b'`。
比较时先看是不是同一个对象（`is`），再看 hash 是否相等，最后才调 `==`，便宜的检查放在前面。

### 扩容

`entries` 用满（大约是 `indices` 长度的 2/3）就换一套更大的表，把还活着的记录按新的长度重新插一遍。
墓碑和 `entries` 里删出来的空洞在这一步一起被清理掉。

### set 为什么没有跟着改

`set` 的源码和 `dict` 是两套，它停在第 3 步，没有做第 4 步的拆表：

- **它不需要顺序，也没有 value**。每格只存 `(key, hash)`，比 `dict` 的记录小，拆表省下的空间有限，所以也就**没有顺序**可言。
- **它的主要工作是查「在不在」**。所以它的跳法也不太一样：撞车后先试几个**紧挨着的**格子
  （相邻的格子大概率在同一段 CPU 缓存里，读起来几乎不要钱），还没找到再按扰动跳远。
- 它扩容得也比 `dict` 早，大约 60% 满就扩，进一步减少跳的次数。

## 复杂度

| 操作 | 均摊 | 最坏 |
|---|---|---|
| `d[k]` / `d[k] = v` / `del d[k]` / `k in d` | O(1) | O(n)（全冲突） |
| `s.add(x)` / `x in s` / `s.discard(x)` | O(1) | O(n) |
| 遍历 | O(n) | |
| `s & t` | O(min(len s, len t)) | |
| `s \| t` | O(len s + len t) | |

## 由此而来的坑

- **list 不能当 key**：可变 → 不可哈希。转成 `tuple(lst)`；字母异位词分组常用 `tuple(sorted(s))` 或 26 位计数元组。
- **`d[k]` 不存在会抛 `KeyError`**：计数用 `d.get(k, 0) + 1`、`defaultdict(int)` 或 `Counter`。
- **`defaultdict` 一读就插**：`if d[k]:` 这种「只是看看」也会把 `k` 塞进去，之后遍历 / `len` 都变了。只读用 `k in d` 或 `d.get(k)`。
- **遍历时改大小**：`for k in d: del d[k]` 直接 `RuntimeError`。遍历 `list(d)`。
- **以为 set 有序**：小整数的 `set` 打印出来常常「看着」有序，那是哈希值恰好等于自己，不是保证。

## 常用的三个变体

| | 用在 |
|---|---|
| `collections.Counter` | 计数；`c.most_common(k)`；两个 Counter 能直接 `==` 比（滑窗异位词） |
| `collections.defaultdict(list)` | 分组：`g[key].append(x)` |
| `collections.OrderedDict` | 要 `move_to_end` / `popitem(last=False)` 的时候 —— 手写 LRU 的偷懒版 |
