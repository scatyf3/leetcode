
### dfs or not

思考，感觉这个东西是 - 因为inplace修改，所以需要一个临时的结构储存顺序

其实有不同写法，迭代和递归都行，官方推荐的solution是？ 
迭代，免于用stack空间

那为啥有些tree之类的就必须dfs，linkedin list不用，和他们有无分支，是否一条道走到黑有关吗

你的直觉对了一半。真正的判据不是"有没有分叉"，而是递归栈里到底存了什么。它只存两样东西：
1. 还没走的分支（待办事项）——走完左子树得回来走右子树
2. 回上来之后还要用的状态（现场）——比如 head.next.next = head 里那个 head


链表这两样都不需要：
1. 没分叉 → 待办永远是 0 个，"下一步去哪"完全由 curr.next 决定，不用记
2. 翻转这个动作可以在下去的路上做完 → 不需要回来

不过两边都有反例，这才是有意思的地方：
1. 树也能 O(1)——Morris 遍历。它把当前节点的前驱那根空着的 right 指针临时接回自己，走完再拆掉。也就是说：它是硬造出了一根"回去的路"，让树暂时退化成能一条道走到黑的结构。这恰好从反面证明了，链表 O(1) 的真正原因是**"回去的路"本来就编码在指针里，不用额外存**。
2. 链表也能被迫用栈——如果题目要求你必须先知道后面的信息才能处理前面的（真·后序）。比如 [234. 回文链表]，比较第 1 个和第 n 个。但链表的标准解法是把后半段原地翻转，而不是压栈——又是同一招：拿指针本身当存储。

所以这里的判断根据是
问题	需要栈吗
一个位置有 ≥2 个后继要访问	需要，存待办分支
必须先拿到后继的结果才能处理当前（后序/自底向上）	需要，存现场
边走边算得出答案（前序/尾递归）	不需要，塌成循环

### 迭代什么

为什么这里要处理三个元素，prev，curr和next，而不是只处理两个？ 
因为 curr.next = prev 这一步是破坏性写入——它覆盖掉的正是你唯一通往后半截链表的路。

拿两个指针试一遍就看到了，1->2->3，prev=None, curr=1：

```
curr.next = prev    # 1.next = None  ← 到 2、3 的唯一引用刚被抹掉
prev = curr         # prev = 1
curr = ???          # 想走到 2，但 2 已经找不到了
```

键是别把它数成"三份状态"：

prev 和 curr 是真状态——翻转一条边必须同时知道两个端点，少一个都不行，所以下界就是 2
nxt 是临时寄存器，生命周期只有一行，跨不过循环边界
对照尾递归版就很清楚，函数签名是 dfs(prev, curr)——只有两个参数，nxt 是函数体里的局部变量。真正需要跨迭代携带的状态确实只有 2 个。这和 a, b = b, a 交换两个变量必须借个 tmp 是同一件事。

你那个多重赋值版本：


head.next, prev, head = prev, head, head.next
没有消灭这个 tmp，只是把它藏了——Python 先把右边整个求值成元组 (prev, head, head.next)（此时用的全是旧值），这个元组就是那个临时变量，然后才往左边赋值。所以它没有更省，只是更容易写错，展开成四行更好。

顺带一个反证：如果是双向链表，就真的不需要 nxt 了。


while curr:
    curr.prev, curr.next = curr.next, curr.prev   # 交换，不是覆盖
    curr = curr.prev                              # 旧的 next 现在躺在 prev 里

### prev+curr or curr+next

这里至少需要两个iter元素+tmp，然而为什么这两个iter元素是 prev+curr 而非 curr+next ? 

因为 nxt 是 curr 的函数——nxt = curr.next，随时能算出来。两个能互相推导的变量，信息量只顶一个。而 prev 你推导不出来。

把循环中间任意一刻画出来看，链表被切成两半：


已翻转                  未处理
None <- 1 <- 2    |    3 -> 4 -> 5
             ↑    |    ↑
           prev   切口  curr
两个真状态必须分别落在切口的两侧，各自是那一半的头。原因是：

prev（左半的头）不可达。左半所有指针都朝左指、背对着你，从 curr 出发永远回不去 prev。你手一松它就彻底丢了。而 curr.next = prev 这个动作偏偏需要它——它是掉头的目的地。
curr（右半的头）不可达。同理，从 prev 出发也走不到 curr（prev 已经掉头朝左了）。
一旦你选 curr + nxt，两个指针都在切口右边，左半那截就完全失联了，掉头没有目的地可写。而且 nxt 还是 curr 推得出来的，等于白拿一个。

这也正好解释了为什么 nxt 只配当 tmp：能从状态里算出来的东西不是状态。它存在的唯一理由是 curr.next = prev 会把它抹掉，所以要在抹掉前抢救一行——一被消费完，下一轮又能从新的 curr 重新算出来。

所以本质上两个iter元素是处理和不处理的分界口？ ✅
